## TL;DR

Windows TerminalからSSH接続し、その中で`tmux`を起動すると、`11;rgb:0c0c/0c0c/0c0c`のような文字列が出ることがありました。

`tmux.conf`に次を追加すると解消しました。

```tmux
set -sg escape-time 100
```

## 症状

表示された文字列は次のようなものでした。

```text
11;rgb:0c0c/0c0c/0c0c
```

環境によっては、次のように見えることもあります。

```text
]11;rgb:0000/0000/0000\
```

見た目はゴミ文字ですが、ランダムな文字列というより、端末制御に使われる応答の一部が漏れて見えている可能性があります。

## 対策

`tmux.conf`に次を追加して直りました。

```tmux
set -sg escape-time 100
```

tmuxを再起動して反映確認をします。

```bash
tmux kill-server
tmux
```

もし`100`で直らなければ、次も候補です。

```tmux
set -sg escape-time 500
```

ただし、大きくしすぎるとESC周りの操作感が少し鈍ることがあります。

## 原因

今回の現象は、`tmux`が端末に送る問い合わせの応答が、正常に内部処理されず、画面や入力として漏れてしまう問題として考えると理解しやすいです。

特に`Windows Terminal + Windowsのssh.exe + tmux`の組み合わせでは、`OSC 11`の応答がそのまま見える報告があります。

つまり`11;rgb:0c0c/0c0c/0c0c`は、配色設定ファイルが壊れて出ているというより、端末制御用の応答が漏れている可能性が高い、という整理です。

参考:
- [Windows Terminal issue #18004](https://github.com/microsoft/terminal/issues/18004)
- [Win32-OpenSSH issue #2275](https://github.com/PowerShell/Win32-OpenSSH/issues/2275)

:::details 用語メモ
- `OSC 11`: 端末の背景色に関する問い合わせや応答で使われる制御シーケンスの一種
:::

## なぜ`escape-time 100`で直るのか

`escape-time`は、`tmux`が`ESC`で始まる入力を見たときに、それが単独のESCキーなのか、続きのある制御シーケンスなのかを判断するための待ち時間です。

この値が短すぎると、少し遅れて届いた応答を`tmux`がうまくまとめて処理できず、結果として制御文字列の一部が漏れることがあります。

今回は`10ms`では足りず、`100ms`に伸ばすことで、一連の応答として吸収できるようになったと考えるのが自然です。

:::details 用語メモ
- `単独のESC`: キーボードのESCキーそのもの
- `制御シーケンス`: 文字の表示ではなく、端末の動作を制御するための特殊な文字列
:::

## なぜ`escape-time`が`500`から`10`に変更されたのか

`escape-time`の既定値が短くなったのは、tmux開発側が「`500ms`は現代の環境では長すぎる」と判断したためです。

tmuxのissueでは、`500ms`という値は昔なら妥当でも、今のローカル環境や低遅延なSSH接続では長すぎて、体感上のもたつきにつながると説明されています。

特に、ESCキーを多用するVimや、Metaキーを使うシェル操作では、`escape-time`が長いほど反応の遅さが目立ちやすくなります。

議論の中では、`0ms`でも問題ない環境は多いものの、既定値としては攻めすぎる可能性があるため、より無難な落としどころとして`10ms`が妥当だと判断されました。

実際にtmuxのメンテナも`10`は「今どき十分に妥当そうだ」とコメントしており、その後、変更が取り込まれています。

その結果、tmux 3.5系では既定値が`500ms`から`10ms`に変更されました。

ただし、この変更は「一般的な操作感を良くする」方向の調整です。そのぶん、今回のように端末応答が少し遅れたり、途中で分割されて届いたりする環境では、逆に短すぎて問題が表面化しやすくなった可能性があります。
